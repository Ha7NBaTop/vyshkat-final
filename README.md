# ВышКат

Консольное приложение учёта транспорта и вещей на C++20. Оно продолжает исходный проект студента: сохранены имена классов, конструкторы с `int id` первым аргументом, метод `dailyEnergyKWh()`, технические характеристики и их проверки. Данные хранятся в памяти до завершения программы.

## Сборка и запуск

В WSL Ubuntu нужны GCC с C++20, CMake 3.20+, Google Test. Python 3.9+ нужен для дополнительных сценариев консоли и скрипта покрытия. Установка отсутствующих зависимостей:

```sh
sudo apt update
sudo apt install build-essential cmake libgtest-dev python3
```

Из папки проекта:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j 2
ctest --test-dir build --output-on-failure
./build/vyshkat
```

Google Test берётся из установленного пакета. DI-контейнер включён в `third_party/boost-di`; скачивания при сборке нет. Сборка только приложения без Google Test доступна в отдельном каталоге:

```sh
cmake -S . -B build-app -DBUILD_TESTING=OFF
cmake --build build-app -j 2
```

## Меню и демонстрация

| Команда | Действие |
|---|---|
| 1 | Приём велосипеда после техосмотра |
| 2 | Приём электросамоката после техосмотра |
| 3 | Добавление шлема |
| 4 | Добавление зарядной станции |
| 5 | Количество транспорта, вещей, общий баланс и суточная энергия |
| 6 | Принятый транспорт для новичков: простота ≥6 |
| 7 | Наименования и номера всего инвентаря |
| 8 | Демонстрация успешного приёма, отказов, вещей и всех отчётов |
| 0 | Выход |

```sh
printf '8\n0\n' | ./build/vyshkat
```

В пустом парке демонстрация принимает велосипед 1001 (простота 6, износ 30%) и самокат 1002 (простота 5, батарея 70%, энергия 2), отклоняет велосипед 1003 (износ 31%) и самокат 1004 (батарея 69%), добавляет шлем 1005 и станцию 1006 (энергия 3). Результат: 2 транспорта, 2 вещи, всего 4 объекта и 5.00 кВт·ч за сутки; новичкам подходит только 1001. Отказы не увеличивают счётчики и энергию. Если номера 1001–1006 уже заняты, демонстрация отменяется до добавлений.

Дробная часть энергии вводится через точку. Нечисловой ввод, лишние символы и переполнение числа вызывают повторный запрос. Нарушение доменного диапазона отменяет операцию и возвращает меню. EOF завершает программу, в том числе посреди добавления, без сохранения незавершённого объекта.

## Модель

`IInventory` задаёт имя и инвентарный номер. `Transport` и `Item` реализуют этот контракт и хранят проверенный `InventoryNumber`. `Transport` также хранит простоту 1–10. Его наследники — `Bicycle` и `ElectricScooter`; наследники `Item` — `Helmet` и `ChargingStation`.

`IEnergyUser` — отдельная способность потреблять энергию. Её реализуют самокат и зарядная станция. У велосипеда и шлема нет фиктивного энергетического метода. Энергия измеряется в кВт·ч за сутки; здоровье батареи в процентах является другой характеристикой.

Примеры конструкторов:

```cpp
Bicycle bicycle(101, 6, 30);                    // id, простота, износ
ElectricScooter scooter(102, 5, 70, 2.0);       // id, простота, батарея, энергия
Helmet helmet(103);
ChargingStation station(104, 3.0);
```

`Park` владеет объектами через `std::unique_ptr`. Транспорт проходит проверку внедрённым `IServiceCenter` перед сохранением. Возврат `false` означает технический отказ; нарушение входных инвариантов вызывает `std::invalid_argument`. Номер отклонённого транспорта остаётся свободным. Вещи добавляются отдельно, без техосмотра транспорта. Неуспешное добавление не меняет баланс.

`Park::report()` возвращает `transportCount`, `itemCount`, `totalCount`, `dailyEnergyKWh`. Энергия включает все принятые объекты с `IEnergyUser`, в том числе станции. `beginners()` возвращает только принятый транспорт с простотой ≥6; `inventory()` — весь баланс. Возвращаемые указатели не владеют объектами и действуют, пока существует парк. Сотрудники к балансу не относятся и пока не моделируются.

Пороги техосмотра сохранены из исходной реализации: велосипед принимается при износе ≤30%, самокат при здоровье батареи ≥70%. PDF не задаёт эти числа. Наши дополнительные решения: единая уникальность номеров, конечная неотрицательная энергия, проверка переполнения общей суммы и отказ пустым указателям. Положительность номера проверяет существующий тип `InventoryNumber`.

## DI

Используется закреплённая [Boost.Ext.DI v1.3.2](https://github.com/boost-ext/di/tree/v1.3.2). Это проект Boost.Ext, не часть официального дистрибутива Boost. [Лицензия](third_party/boost-di/LICENSE_1_0.txt), источник и контрольные суммы находятся в [описании зависимости](third_party/boost-di/README.md). CMake проверяет SHA256 заголовка.

- DIP: парк зависит от интерфейса `IServiceCenter`.
- Constructor injection: зависимость передаётся в `Park(IServiceCenter&)`.
- DI-контейнер: `main.cpp` регистрирует реализации и создаёт граф `ConsoleApp → Park → IServiceCenter` через `injector.create`.

`main.cpp` — Composition Root. Контейнер также привязывает `std::cin` и `std::cout`; сервис и парк имеют область singleton. Injector остаётся в `main` на время запуска. В этой версии библиотеки singleton хранится как function-static; доменная модель не обращается к нему напрямую. У `Park` нет контейнера или глобального Service Locator. Переданный сервис должен жить дольше парка. В тестах fake создаётся перед парком и внедряется тем же конструктором вручную; это подмена зависимости, а не замена настоящего контейнера в приложении.

## SOLID

1. **Наиболее явный принцип — DIP:** `Park` получает `IServiceCenter`, а Composition Root выбирает `ServiceCenter`. Fake меняет решение техосмотра без изменения парка.
2. **Сознательно ограничен OCP:** `ServiceCenter` хранит правила по точному `typeid`, неизвестный тип отклоняет. `registerRule<T>` добавляет правило без изменения `inspect`. Новый транспорт всё равно требует регистрации и команды меню. Производный от велосипеда тип не наследует допуск автоматически. Для небольшой программы явное меню проще системы плагинов.
3. **Расширение:** новому транспорту нужны наследник `Transport`, при необходимости `IEnergyUser`, правило техосмотра и ввод в меню. Отчёты парка менять не нужно. Новая вещь наследует `Item`. Сотрудник должен быть отдельной сущностью без `IInventory`; склад потребует собственного учёта количества и операций, которые пока не реализованы.
4. **Тесты и подмена:** `ParkTest.RejectedTransportIsAbsentFromEveryViewAndReport` проверяет отказ и неизменность всех отчётов; `InjectedServiceCanAcceptTechnicallyUnsuitableTransport` показывает, что решение принимает fake. `BeginnersIncludeSimplicitySixButExcludeFive` закрепляет границу 5/6. `FakeServiceCenter` реализует интерфейс и передаётся в конструктор `Park`.
Остальные принципы:

- **SRP:** сущности проверяют свои значения, сервис решает техосмотр, парк хранит принятые объекты, консоль читает и форматирует данные.
- **LSP:** наследники поддерживают общий контракт имени/номера, транспорт — также простоту. Шлем не обязан реализовывать поездку или зарядку. Технический отказ является политикой отдельного сервиса.
- **ISP:** инвентаризация и энергия разделены; `IServiceCenter` содержит одну операцию техосмотра.

## Проверки и покрытие

Сохранён смысл исходных проверок характеристик, номера и технических границ; вызовы конструкторов обновлены. Добавлены проверки интерфейсов, пустого парка, отказа без изменения отчётов, границы 5/6, смешанной энергии, дублей, повторного использования отклонённого номера, переполнения, расширения модели и ввода/EOF.

`ctest` при наличии Python запускает также `CliSmoke`: 11 сценариев реального исполняемого файла, включая его DI-сборку. Сохранить полный вывод сценариев:

```sh
python3 scripts/smoke.py build/vyshkat --output-dir validation/cli
```

Для измерения покрытия используйте отдельную GCC-сборку:

```sh
cmake -S . -B build-coverage -DCMAKE_BUILD_TYPE=Debug -DVYSHKAT_COVERAGE=ON
cmake --build build-coverage -j 2
ctest --test-dir build-coverage --output-on-failure
python3 scripts/coverage.py build-coverage --output validation/coverage-summary.json
```

Скрипт считает уникальные исполняемые строки собственного кода `src/*.cpp` и `src/*.hpp`, объединяет копии inline-строк, исключает тесты, сторонний код и системные заголовки. Это метрика строк, не ветвей; в неё входят unit-тесты и сценарии CLI. Ориентир PDF — ≥60%. Проверка 18 октября 2026 года: 31/31 проверок CTest прошли, включая 11 сценариев CLI; покрытие — 99,23% (259 из 261 уникальных исполняемых строк). Подробные журналы и отчёты сохраняются локально в `validation/`; эта папка исключена из Git. Скрипты из `scripts/` входят в репозиторий и позволяют повторить проверки.

Сохранения между запусками, БД, GUI, оплаты и кадрового учёта нет. Имена типов и часть ошибок остаются на английском. Основная проверенная среда — GCC в WSL Ubuntu; проверка другими компиляторами не заявляется.
